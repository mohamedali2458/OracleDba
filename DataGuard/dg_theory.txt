What Is Oracle Data Guard?
Oracle Data Guard is a high availability (HA) and disaster 
recovery (DR) solution that ensures data protection and 
business continuity by maintaining standby databases 
synchronized with a primary database.


The standby database can be:

	On the same data center
	On a remote site
	On Oracle Cloud Infrastructure (OCI)

Changes made on the primary database are transferred and 
applied to the standby database using redo data.

Why Do We Need Data Guard?

Without Data Guard:
	Database failure = extended downtime
	Risk of data loss
	Manual recovery procedures
	Complex restore operations

With Data Guard:
	Automated redo synchronization
	Minimal or zero data loss
	Fast role transitions (switchover/failover)
	Production-grade DR strategy

Types of Standby Databases
	Oracle Data Guard supports multiple standby types:

1. Physical Standby
	Exact block-for-block copy of the primary database
	Redo is applied using media recovery
	Supports Active Data Guard (read-only access)
	Most commonly used in production

2. Logical Standby
	Data is transformed into SQL and applied
	Supports read/write operations for reporting
	More complex to maintain
	Limited object support

3. Snapshot Standby
	Temporary, updateable standby
	Useful for testing and QA
	Can be reverted back to physical standby


Oracle Data Guard Architecture Overview

At a high level, Data Guard consists of:

	Primary Database — Production database
	Standby Database — DR database
	Redo Transport Services — Ships redo
	Apply Services — Applies redo on standby
	Data Guard Broker (optional) — Automation and management

Basic Flow:
	User commits transaction on primary
	Redo is generated
	Redo is shipped to standby
	Standby applies redo
	Databases remain synchronized

Key Data Guard Processes (Internals)
	Understanding these background processes is critical for troubleshooting.

On Primary Database:
	LGWR (Log Writer)
	Writes redo to online redo logs

	LNS (Log Network Service)
	Ships redo to standby in real-time

	ARCn (Archiver)
	Ships archived redo logs

On Standby Database:
	RFS (Remote File Server)
	Receives redo from primary

	MRP (Managed Recovery Process)
	Applies redo to standby database

Redo Transport Modes
	Redo transport defines how redo is shipped to the standby.

SYNC
	Redo is confirmed at standby before commit completes
	Zero data loss
	Higher latency

ASYNC
	Redo is shipped asynchronously
	Better performance
	Minimal data loss possible

Data Guard Protection Modes
	Oracle Data Guard supports three protection modes:

Maximum Protection
	Zero data loss
	SYNC + AFFIRM
	Primary shuts down if standby unavailable

Maximum Availability
	Zero data loss (when possible)
	Best balance of safety and uptime

Maximum Performance
	ASYNC transport
	Best performance
	Small risk of data loss

Role Transitions in Data Guard
	Data Guard allows smooth role changes:

Switchover
	Planned role reversal
	No data loss
	Used during maintenance

Failover
	Unplanned role transition
	Used during disasters
	Standby becomes new primary
